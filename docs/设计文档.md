# 请假审批系统（OA）— 业务与接口设计

> DDD 练习项目配套设计文档。后端代码由你手写，本文档定义业务规则、领域模型建议、全部接口的入参/出参与数据库表设计。
> 登录注册与权限控制同样由你在后端实现，前端只做表单与凭证透传。

---

## 1. 业务场景概述

员工注册账号（选择所属部门）并登录后提交请假申请，部门主管审批，审批通过后扣减对应假期余额；支持撤回、取消、销假等全生命周期管理。员工可修改自己的姓名，主管可新增部门、调整员工归属部门。

### 1.1 参与角色

| 角色 | 编码 | 来源 | 职责 |
|------|------|------|------|
| 员工 | `STAFF` | 注册接口自助创建（默认角色） | 创建/编辑/提交请假单，撤回，取消，查看余额，修改自己姓名 |
| 主管 | `MANAGER` | 初始化种子数据提供（或后续做角色管理扩展） | 审批（通过/驳回），新增部门，员工调岗，查看员工列表；同时拥有员工全部能力 |

### 1.2 认证与权限设计（由你实现）

- **凭证机制**：登录成功后后端签发 token，前端保存并在后续请求头携带 `Authorization: Bearer {token}`。
  token 实现方式二选一：
  - 方案 A（推荐入门）：UUID token + `t_auth_token` 表（含过期时间），登出即删记录，实现直观，顺便练拦截器 + 仓储；
  - 方案 B（进阶）：JWT（HMAC 签名），无状态但需自行处理登出失效与续期。
- **注册规则**：用户名全局唯一（4~32 位字母/数字/下划线），密码 6~32 位，后端必须 BCrypt 等慢哈希存储，禁止明文；姓名 2~32 字；`departmentCode` 必填且必须存在于部门表（引用校验）。注册角色固定为 `STAFF`，前端不提供角色选择。
- **鉴权拦截**：除 `POST /auth/register`、`POST /auth/login`、`GET /departments`（注册下拉需要）外，所有接口都要求有效 token；无效/过期返回 `40100`，前端收到后清除本地凭证并跳转登录页。
- **权限控制**：三层校验全部在后端——
  1. 认证拦截器：token → 当前账号（对应 `40100`）；
  2. 角色校验：`MANAGER` 专属接口（审批、待审批列表、员工列表、新增部门、调岗），非主管返回 `40300`；
  3. 资源归属校验：编辑/提交/撤回/取消/销假仅限单据申请人本人，审批人不能审批自己的单据，返回 `40300`。

### 1.3 假期类型

| 类型 | 编码 | 说明 |
|------|------|------|
| 年假 | `ANNUAL` | 每年固定额度 |
| 病假 | `SICK` | 每年固定额度 |
| 事假 | `PERSONAL` | 每年固定额度 |

### 1.4 请假单状态机（核心领域规则）

```
DRAFT（草稿）
  │ 提交 submit
  ▼
SUBMITTED（已提交）──→ 撤回 withdraw ──→ DRAFT（回到草稿，可再编辑）
  │ │
  │ └─→ 审批通过 approve ──→ APPROVED（已通过，扣减余额）
  │        │
  │        ├─→ 取消 cancel（开始日之前）──→ CANCELLED（已取消，回滚余额）
  │        └─→ 销假 close ──→ CLOSED（已销假/已完结）
  │
  └─→ 审批驳回 reject ──→ REJECTED（已驳回，终态；重新请假需新建请假单）
```

状态编码：`DRAFT` / `SUBMITTED` / `APPROVED` / `REJECTED` / `CANCELLED` / `CLOSED`

> 这个状态机正好可以落在你项目里已有的 `StatusMachine` 接口上：每个状态枚举实现 `getFlowToCollection()` 声明合法流转，`flowTo()` 校验非法流转并抛异常。

### 1.5 业务规则（领域层校验，全部在后端执行）

1. **余额校验**：提交时校验对应年度假期余额充足；审批通过时扣减余额；取消时回滚余额。（可进阶：提交时预占、通过时正式扣减）
2. **时长计算**：请假时长 = 起止日期的自然日天数（`endDate - startDate + 1`）。进阶练习：改为工作日计算（跳过周末），作为领域服务实现。
3. **时间校验**：开始日期不得早于提交当日；结束日期不得早于开始日期；单次请假不超过 30 天。
4. **重叠校验**：同一员工不允许存在时间重叠且状态为 `SUBMITTED` / `APPROVED` 的请假单。
5. **操作权限**（见 1.2 第三层校验）：本人才能操作自己的单据；仅 `MANAGER` 可审批且不能审批自己的请假单。
6. **取消限制**：已通过的请假单只能在开始日期当天 00:00 之前取消。
7. **驳回意见**：驳回时必须填写驳回原因（1~200 字）。
8. **并发控制**：请假单更新使用乐观锁（`version` 字段），余额扣减同样需要。
9. **姓名规则**：2~32 字；注册与改名共用同一条规则（规则已出现在两处，建议抽 `Name` 值对象，构造即校验）。
10. **部门归属**：注册与调岗时 `departmentCode` 必须存在于部门表；部门名全局唯一；调岗仅针对 `STAFF`（主管账号不参与调岗）。

### 1.6 领域模型建议（供参考，具体由你实现）

随着"改名""部门查表"的加入，账号与员工档案是两个概念，建议分两个域：

- **auth 域（认证与访问）**：
  - 聚合根 `Account`（username 作为标识、`Password` 值对象、`Role` 枚举、关联 employeeCode）；
  - 实体 `AuthToken`（token、过期时间；签发/校验算法放 infrastructure）；
  - 仓储 `AccountRepository`、`AuthTokenRepository`。
- **employee 域（组织与档案）**：
  - 实体 `Employee`（工号 code、`Name` 值对象 2~32 字、departmentCode 引用），行为：`rename()`；
  - 实体 `Department`（code、name 唯一）；
  - 仓储 `EmployeeRepository`、`DepartmentRepository`。
- **leave 域（请假）**：
  - 聚合根 `LeaveRequest`（内含审批记录列表；code 作为聚合标识）；
  - 值对象 `LeavePeriod`（startDate + endDate + duration，含时长计算与重叠判断）、`LeaveType`；
  - 领域服务：余额校验/扣减（跨聚合：请假单 ↔ 余额）；
  - 领域事件（进阶）：`LeaveRequestSubmitted`、`LeaveRequestApproved`（监听后扣余额）、`LeaveRequestRejected`、`LeaveRequestCancelled`（回滚余额）、`LeaveRequestClosed`；
  - 仓储 `LeaveRequestRepository`、`LeaveBalanceRepository`。
- 注册流程是**跨域编排**（应用层）：创建 Employee 档案 → 创建 Account → 初始化当年余额。

## 2. 接口设计

### 2.0 通用约定

- Base URL：`/api/v1`
- 认证：除 **注册、登录、部门列表** 外，所有请求需携带请求头 `Authorization: Bearer {token}`。
- 统一响应包装：

```json
{ "code": 0, "message": "success", "data": { } }
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 0 成功；非 0 失败，见错误码表 |
| message | string | 提示信息，前端直接展示 |
| data | object/null | 业务数据，失败时为 null |

错误码约定：

| code | 含义 |
|------|------|
| 0 | 成功 |
| 40000 | 参数校验失败（message 返回具体原因） |
| 40100 | 未登录或凭证无效/过期（前端收到后清除凭证跳登录页） |
| 40300 | 已登录但无权执行该操作（角色不符或非资源归属人） |
| 40400 | 资源不存在（员工/请假单/部门） |
| 40900 | 冲突（用户名/部门名已存在） |
| 41001 | 状态流转非法（对应状态机异常） |
| 41002 | 假期余额不足 |
| 41003 | 请假时间与其他单据重叠 |
| 41004 | 请假时间不合法（开始日期过早/区间非法/超 30 天） |
| 41005 | 乐观锁冲突，请刷新后重试 |
| 50000 | 系统内部错误 |

分页请求统一参数：`page`（1 起）、`size`（默认 10）；分页响应统一结构：

```json
{ "list": [], "total": 100, "page": 1, "size": 10 }
```

### 2.1 注册

`POST /api/v1/auth/register`（免 token）

**入参**（body）：

```json
{
  "username": "zhangsan",
  "password": "123456",
  "name": "张三",
  "departmentCode": "D001"
}
```

| 字段 | 类型 | 必填 | 校验 |
|------|------|------|------|
| username | string | 是 | 4~32 位，仅字母/数字/下划线，全局唯一（重复返回 40900） |
| password | string | 是 | 6~32 位 |
| name | string | 是 | 2~32 字（与改名共用规则，见 2.7） |
| departmentCode | string | 是 | 必须存在于部门表（不存在返回 40400） |

**出参** `data`：注册成功即视为登录成功，直接签发 token：

```json
{
  "token": "9f8b7c6d-...-a1b2c3d4e5f6",
  "user": {
    "code": "EMP006",
    "username": "zhangsan",
    "name": "张三",
    "departmentCode": "D001",
    "departmentName": "研发部",
    "role": "STAFF"
  }
}
```

> 注册是跨域编排：创建 Employee 档案 → 创建 Account → 初始化当年三类假期余额。

---

### 2.2 登录

`POST /api/v1/auth/login`（免 token）

**入参**（body）：

```json
{ "username": "zhangsan", "password": "123456" }
```

**出参** `data`：结构同 2.1。用户名不存在或密码错误统一返回 `40000`，message 固定为"用户名或密码错误"（不暴露具体是哪个错）。

**token 约定**：有效期建议 7 天，过期/登出后校验失败返回 `40100`。

---

### 2.3 退出登录

`POST /api/v1/auth/logout`（需 token）

**入参**：无 body。

**出参** `data`：`null`。方案 A 直接删除 token 记录；JWT 方案可只返回成功（配合前端清除）。

`GET /api/v1/auth/me`（需 token）

**入参**：无。

**出参** `data`：结构同 2.1 中的 `user`。

### 2.11 创建请假单（草稿）

`POST /api/v1/leave-requests`（需 token）

**入参**（body）：

```json
{
  "leaveType": "ANNUAL",
  "startDate": "2026-10-01",
  "endDate": "2026-10-03",
  "reason": "国庆回家探亲"
}
```

| 字段 | 类型 | 必填 | 校验 |
|------|------|------|------|
| leaveType | string | 是 | 枚举：ANNUAL/SICK/PERSONAL |
| startDate | string | 是 | 格式 yyyy-MM-dd |
| endDate | string | 是 | 格式 yyyy-MM-dd，≥ startDate |
| reason | string | 是 | 1~200 字 |

**出参** `data`：请假单完整对象（结构同 2.13 详情），创建后状态为 `DRAFT`。申请人取当前登录用户。

### 2.12 修改请假单（仅 DRAFT 可改）

`PUT /api/v1/leave-requests/{code}`（需 token，仅申请人本人）

**入参**：同 2.11，另加路径参数 `code`；body 中额外携带：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| version | int | 是 | 乐观锁版本号，取详情接口返回值 |

**出参** `data`：请假单完整对象。

### 2.13 请假单详情

`GET /api/v1/leave-requests/{code}`（需 token；本人或 `MANAGER` 可查）

**入参**：路径参数 `code`

**出参** `data`：

```json
{
  "code": "LV20260916001",
  "applicantCode": "EMP006",
  "applicantName": "张三",
  "department": "研发部",
  "leaveType": "ANNUAL",
  "leaveTypeName": "年假",
  "startDate": "2026-10-01",
  "endDate": "2026-10-03",
  "duration": 3,
  "reason": "国庆回家探亲",
  "status": "SUBMITTED",
  "version": 1,
  "createdAt": "2026-09-16 10:30:00",
  "updatedAt": "2026-09-16 11:00:00",
  "approvalRecords": [
    {
      "approverCode": "MGR001",
      "approverName": "赵总",
      "action": "REJECT",
      "comment": "项目上线期间，建议错峰",

```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | string | 请假单号，格式 `LV + yyyyMMdd + 3位序列`（生成规则由你定） |
| duration | int | 自然日天数，后端计算 |
| status | string | DRAFT/SUBMITTED/APPROVED/REJECTED/CANCELLED/CLOSED |
| version | int | 乐观锁版本 |
| approvalRecords | array | 审批记录，按时间倒序；action：APPROVE/REJECT |

**入参**：路径参数 `code`

### 2.18 销假（APPROVED → CLOSED）

`POST /api/v1/leave-requests/{code}/close`（需 token，仅申请人本人）

**入参**：路径参数 `code`。业务含义：假期结束确认单据完结（实际休假天数与申请一致时直接关闭；进阶可做"实际提前返岗按实际天数回滚差额余额"）。

**出参** `data`：请假单完整对象。

---

### 2.19 审批（`MANAGER` 专属）

`POST /api/v1/leave-requests/{code}/approve`（需 token，角色 `MANAGER`，且不能审批自己的单据）

**入参**（body）：

```json
{
  "action": "APPROVE",
  "comment": "同意",
  "version": 1
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| action | string | 是 | APPROVE / REJECT |
| comment | string | 否(通过)/是(驳回) | 审批意见；REJECT 时必填 1~200 字 |
| version | int | 是 | 乐观锁版本号 |

**出参** `data`：请假单完整对象。APPROVE 成功后余额已被扣减。

## 3. 数据库设计

> 完整可执行 DDL 见 [schema.sql](./schema.sql)（H2，URL 加 `;MODE=MySQL` 可原样运行）。本节说明表结构与设计意图。

### 3.0 表关系总览

```
t_department (1)───(N) t_employee (1)───(1) t_account (1)───(N) t_auth_token
                           │ (1)
                           ├─(N) t_leave_balance                     按 员工+类型+年度 唯一
                           └─(N) t_leave_request ──┬─(N) t_leave_approval_record   审批记录（聚合内）
                                                   └─(N) t_leave_request_log      状态流转日志（领域事件驱动，可选）
```

- 账号与员工档案**分表**：`t_account` 管登录凭证与角色（auth 域），`t_employee` 管姓名/部门归属（employee 域），一一对应——对应"Account 与 Employee 是两个概念"的建模。
- 所有表间关系均为**逻辑外键**（存 code，不建物理外键约束），符合聚合边界：审批记录隶属请假单聚合，只能随聚合一起加载/修改。
- 余额表独立于请假单聚合，跨聚合的扣减/回滚通过领域服务完成，并发用乐观锁（version）。

### 3.1 t_department 部门表（实体）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| code | VARCHAR(32) | PK | 部门编码，如 D001 |
| name | VARCHAR(64) | UNIQUE, NOT NULL | 部门名，全局唯一 |
| created_at | DATETIME | NOT NULL | 创建时间 |

### 3.2 t_employee 员工档案表（employee 域实体）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| code | VARCHAR(32) | PK | 员工工号（对应 AbstractCode），如 EMP006 |
| name | VARCHAR(64) | NOT NULL | 姓名（`Name` 值对象，2~32 字，注册/改名共用规则） |
| department_code | VARCHAR(32) | NOT NULL | 归属部门（引用校验 t_department） |
| join_date | DATE | | 入职日期（进阶：按工龄生成年假额度） |
| created_at / updated_at | DATETIME | NOT NULL | 创建/更新时间 |

### 3.3 t_account 账号表（auth 域聚合根）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| username | VARCHAR(32) | PK | 登录用户名即账号标识（4~32 位字母/数字/下划线） |
| password | VARCHAR(100) | NOT NULL | 密码哈希（BCrypt 等），禁止明文 |
| role | VARCHAR(16) | NOT NULL | STAFF / MANAGER；注册固定 STAFF |
| employee_code | VARCHAR(32) | UNIQUE, NOT NULL | 关联员工档案（1:1） |
| created_at / updated_at | DATETIME | NOT NULL | |

### 3.4 t_auth_token 登录凭证表（方案 A；用 JWT 则省略）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| token | VARCHAR(64) | PK | 凭证 UUID |
| username | VARCHAR(32) | NOT NULL, 索引 | 所属账号 |
| expire_at | DATETIME | NOT NULL | 过期时间（建议签发 + 7 天） |
| created_at | DATETIME | NOT NULL | 签发时间 |

登出即删除记录；校验时查不到或已过期 → 返回 40100。

### 3.5 t_leave_balance 假期余额表（实体）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT | PK, 自增 | |
| employee_code | VARCHAR(32) | NOT NULL | 员工工号 |
| leave_type | VARCHAR(16) | NOT NULL | ANNUAL / SICK / PERSONAL |
| year | INT | NOT NULL | 年度 |
| total_days | DECIMAL(5,1) | NOT NULL | 年度总额度（支持半天） |
| used_days | DECIMAL(5,1) | NOT NULL DEFAULT 0 | 已用天数（审批通过扣减） |
| frozen_days | DECIMAL(5,1) | NOT NULL DEFAULT 0 | 预占天数（进阶方案用，简化恒为 0） |
| version | BIGINT | NOT NULL DEFAULT 0 | 乐观锁版本 |
| created_at / updated_at | DATETIME | NOT NULL | |

- 唯一约束：`(employee_code, leave_type, year)`
- CHECK：`used_days >= 0 AND frozen_days >= 0`（数据库层兜底，领域层同样校验）

### 3.6 t_leave_request 请假单表（聚合根 LeaveRequest）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| code | VARCHAR(32) | PK | 请假单号：LV + yyyyMMdd + 3 位序列 |
| applicant_code | VARCHAR(32) | NOT NULL | 申请人工号 |
| leave_type | VARCHAR(16) | NOT NULL | ANNUAL / SICK / PERSONAL |
| start_date | DATE | NOT NULL | 开始日期 |
| end_date | DATE | NOT NULL | 结束日期（含当天） |
| duration | DECIMAL(4,1) | NOT NULL | 时长（天），后端计算 |
| reason | VARCHAR(500) | NOT NULL | 请假事由 |
| status | VARCHAR(16) | NOT NULL | DRAFT/SUBMITTED/APPROVED/REJECTED/CANCELLED/CLOSED |
| version | BIGINT | NOT NULL DEFAULT 0 | 乐观锁版本 |
| submit_time | DATETIME | | 提交时间 |
| finish_time | DATETIME | | 终态时间（通过/驳回/取消/销假） |
| created_at / updated_at | DATETIME | NOT NULL | |

- CHECK：`end_date >= start_date`、`0 < duration <= 30`
- 索引：
  - `idx_leave_applicant (applicant_code, status, created_at DESC)` — 我的请假单列表
  - `idx_leave_overlap (applicant_code, start_date, end_date)` — 时间重叠校验

### 3.7 t_leave_approval_record 审批记录表（聚合内实体）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT | PK, 自增 | |
| request_code | VARCHAR(32) | NOT NULL, 索引 | 所属请假单号（聚合外键） |
| approver_code | VARCHAR(32) | NOT NULL | 审批人工号 |
| action | VARCHAR(16) | NOT NULL | APPROVE / REJECT |
| comment | VARCHAR(200) | | 审批意见（驳回时必填） |
| created_at | DATETIME | NOT NULL | |

索引 `idx_approval_request (request_code, created_at DESC)`：详情页按时间倒序取审批记录。一张单可多次提交→撤回→再提交，允许多条记录。

### 3.8 t_leave_request_log 状态流转日志表（可选，建议实现）

| 字段 | 类型 | 约束 | 说明 |
